# 古文単語330 対応計画

## 1. 目的・前提

[classic-japanese-spec.md](./classic-japanese-spec.md) の要件に従い、既存アプリに「古文単語330」を追加するための作業順序、設計方針、検証方法を整理する。チェック項目は実装状況を表す。

> **状況**: Phase 0〜6 はモックデータで実装・検証済み（ユニットテスト、E2E、型チェック、ビルド）。Phase 7 はデータリポジトリの `classic-japanese-330/target` が未配置（Contents API が HTTP 404）のため未着手で、データ提供後に実施する。

### 初回の対象

- 古文教材の追加、見出し語・例文の単語帳出題、古文 → 現代語の自己判定。
- 既存の出題設定、学習履歴、中断・再開、結果、再挑戦との連携。
- POINT・出典ページの表示、複数の意味・例文・表記違いへの対応。
- 既存英語教材の互換性、非対応機能への誤進入防止、ユニットテスト・E2E・関連文書の更新。

### 初回の対象外

- 古文の書き取り、穴埋め、タイピング、落ち物ゲーム、バトル、現代語 → 古文の出題。
- 古文の補足Markdown・書籍画像の取得、データ作成、書籍からの抽出。
- データリポジトリへの書き込み、デプロイ。公開権限の確認はデータ提供側が行う。

### 事前確認結果・外部依存

- 2026-10-31 時点で、`jun-shiromizu/english-idiom-target-1000-data` は公開リポジトリで、既定ブランチは `main`。
- 同日時点で `main` の `classic-japanese-330/target` を Contents API で確認したところ HTTP 404 だった。330ファイルの存在・内容・公開権限は未確認。
- アプリ開発と自動テストは独自のモックデータで先行できる。ただし、実データでの結合確認と本番利用の受け入れは、データ提供・公開権限の確認後に行う。404 を空教材として扱わない。
- 詳細仕様と本書に差異がある場合は仕様を優先する。実装上の新たな仕様変更が必要になった場合は、合意のうえで両方を更新する。

## 2. 計画時に確定した設計方針

### 2.1 問題と履歴の識別

- 提示済みのJSON形式を変更せず、見出し語・例文・訳のテキストを使って識別する。
- 見出し語・例文・訳を修正した場合、その問題は未回答扱いとする。古い履歴を別問題へ割り当てない。
- `senseNumber` は意味の識別に使い、配列の並べ替えで変更しない。
- 区切り文字を含むテキスト同士の衝突を避けるため、区切り文字の単純連結ではなく、型と要素順を定めたJSON配列などをキーとして直列化する。正規化・大文字小文字変換・空白除去は行わない。

履歴キーの構成例。文字列は説明用のプレースホルダーであり、実際の教材内容ではない。

```text
["v1", "classic-japanese-330", "idiom", "classic-to-modern", "0001",
 "word", "〈見出し語〉", 同一内容の件数, 同一内容内の出現順]

["v1", "classic-japanese-330", "sentence", "classic-to-modern", "0001",
 "example", 意味番号, "〈例文〉", "〈現代語訳〉", 同一内容の件数, 同一内容内の出現順]
```

- `classic-to-modern` は内部方向IDの案。表示用の「古文 → 現代語」とは分離し、既存英語の方向IDは変更しない。
- 同一内容の件数・出現順を含め、完全に同じ見出し語や同じ意味内の同一例文が複数あっても、それぞれ独立した問題として記録する。同一内容の件数が増減した場合、その同一内容グループの履歴は引き継がない。
- 内容が完全に同一の要素は、個体としての入れ替えをデータから識別できない。この方式はその制約を受け入れ、件数が変わった際の誤対応を避ける。
- 古文の履歴キーには版を付け、範囲クリアでは解析した教材IDと番号で対象を特定する。英語の既存キー・旧キーは従来どおり読み取り、変更・移行しない。
- 構成例では見出し語・例文・訳の文字列も端末の履歴に保存される。新規開始時の取得キャッシュとしては使わず、保存容量を実測する。
- 修正前の古い履歴は参照されなくなるが、該当教材・番号の範囲クリアまたは全クリアでは削除できるようにする。

### 2.2 古文選択中のバトル再開

- 既存のバトル中断データには出題教材や番号範囲が含まれず、再開時のトップ設定を読み直す。過去の開始時設定を中断データだけから復元することはできない。
- 古文への切り替え直前の英語設定を保持し、古文選択中に既存バトルを再開するときはその英語設定を使う。英語選択中は従来どおり現在の英語設定を使う。
- 実装案として、`idiom-app-settings` の既存項目を維持したまま、直前の英語設定を任意フィールドとして追加する。バトルセッション・デッキの保存形式は変更しない。
- 古文への範囲補正や方向変更より前に英語設定を退避し、古文設定の保存で退避値を上書きしない。旧設定からの初回切り替えも同様に扱う。
- バトル画面とバトル結果画面は共通の設定解決を利用し、教材・番号範囲の表示と問題取得先が食い違わないようにする。
- 古文選択中に有効な退避設定を取得できない場合は、英語教材の選択が必要である旨を通知し、中断データを破棄しない。以前の設定を推測して古文で出題しない。

## 3. 作業順序と依存関係

| Phase | 内容 | 依存 | 完了の目安 |
|---|---|---|---|
| 0 | 現状・データ契約・テスト基盤の確認 | なし | 既存動作と独自フィクスチャを用意 |
| 1 | 教材設定・型・対応可否の基盤 | 0 | 古文と英語を型安全に区別できる |
| 2 | データ取得・検証 | 1 | モックで古文JSONの取得・失敗を検証できる |
| 3 | 問題生成・履歴・セッション | 1 | 複数例文と既存データの互換性を検証できる |
| 4 | 画面・再開・非対応経路の制御 | 2、3 | 単語帳の一連の操作がモックで動作する |
| 5 | 総合テスト・回帰確認 | 4 | 受け入れ条件を自動テストなどで確認する |
| 6 | 関連文書の更新 | 4 | 既存仕様・計画・READMEと実装が一致する |
| 7 | 実データ結合・受け入れ | 5、6、データ提供 | 実データ330件と公開条件を確認する |

Phase 2 と Phase 3 は、Phase 1 の型・契約が固まった後に並行可能。テストは各Phaseと同時に追加し、Phase 5 では統合・回帰を確認する。実データが未提供でも Phase 0〜6 はモックで進められるが、Phase 7 を完了扱いにしない。
